# App 反馈与关于入口

2026-10-10 用户共识；适用于本人 iOS / macOS App 的常规开发、issue 修复与发布维护。

## 已确定的产品结构

- 在 App 自有主设置列表或自定义菜单组末尾，反馈倒数第二，关于最后。
- 反馈直达联系流程；关于显示 App 名和真实版本，并收纳评价此 App、更多作品、开发者网站 `https://norvyn.com`。
- 分享此 App 未纳入必选标准。
- macOS 适配已有 App 菜单 About 与 Help 入口；不机械重排 Apple 系统菜单。已有帮助/反馈捷径可复用同一目的地，避免藏深。
- 不主动催评分。评分由用户主动点击，联系流程只准备草稿，不自动发送。

## 常规检查与缺项处理

每次开发或修复 issue，先读本项目已有入口记录，检查上述入口、实际路由与元数据。优先复用项目索引和上次记录，不为此重新全盘扫描全部 App。

已有 App 的缺项登记并随发版处理；检查、记录不等于已完成 UI，也不意味着本次 issue 必须扩为入口改造。实际 UI 或行为变更遵循当前用户授权范围及既有验收要求，本规范不自动扩权，也不新增审批流程。

项目记录至少包含：检查日期、源项目身份/路径、入口源码位置、现有/缺失/未核验/不适用状态、App Store ID 与证据、公开反馈邮箱与证据、更多作品目标、待补事项和发布验收证据。优先在现有项目索引私有维护笔记中记录；具体实现/验收按项目既有文档约定留档。

App ID、开发者集合 URL、邮箱须标明来源与验证状态。占位值、过期值或未核验值不得描述为可用链接；未上架、非商店分发、平台不适用须注明原因。跨 App 共享信息可集中配置，UI 复用本项目现有组件与样式，避免复制成多份真源。

## 尚未确认的策略

邮件默认诊断字段尚未达成共识。仅预填 App 名和版本是讨论候选，不能据此强制移除既有设备/OS 字段；不改变 Glink 当前反馈行为。不得擅自附加日志、账号或私有数据。是否包含 build、是否保留设备/OS，以及各 App 使用统一或独立邮箱，按用户后续决定。

关于内部行顺序、更多作品使用 Apple 开发者集合还是网站集合、缺元数据时行的呈现方式，尚待明确；不要用猜测的开发者 ID 或邮箱补空。
